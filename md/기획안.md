> **Alpha Talk** — "종목 하나 = 방 하나" 컨셉의 통합 주식 정보 커뮤니티 플랫폼
> 뉴스·공시·리포트·AI 요약·유저 글·시세를 **하나의 시간순 스트림**으로 모아 보여주는 종토방형 서비스

## 1. 요구사항 분석

### 1.1 문제 정의 & 배경

개인투자자는 종목 하나를 추적하는 데도 뉴스는 포털, 공시는 DART, 시세·차트는 HTS/MTS, 토론은 종토방, 재무는 또 다른 곳을 오간다. **정보가 파편화**되어 있는 데다 종토방은 노이즈가 많아 신뢰하기 어렵다. 쏟아지는 뉴스를 일일이 읽기도 부담스럽다.

**기회**: "한 종목에 대한 모든 것"을 한 곳에, 시간순으로, AI 요약과 함께 모으면 추적 비용이 크게 준다. 커뮤니티 대화도 그 종목의 실제 이벤트(뉴스·공시) 맥락 위에서 이뤄진다.

### 1.2 타깃 사용자

- **주 타깃**: 소수 관심 종목을 꾸준히 추적하는 개인투자자. 종토방 문화에 익숙한 한국 투자자.
- **페르소나**
    - *추적형* — 보유/관심 종목 5~20개를 매일 확인. 뉴스·공시·시세를 빠르게 훑고 싶다.
    - *대화형* — 종토방을 즐기지만 노이즈에 지쳐 있다. 정보 맥락이 있는 토론을 원한다.
    - *효율형* — 뉴스 읽을 시간이 없어 AI 3줄 요약으로 핵심만 보고 싶다.
### 1.3 핵심 컨셉 & 가치 제안

**종목 = 방, 스트림이 주인공.** 구독한 종목이 "방"이 되고 방에 들어가면 통합 스트림이 흐른다. 모든 정보 조각을 **StreamEvent** 하나의 단위로 정규화해 시간순으로 노출한다.

- **통합** — 내 종목의 모든 정보와 대화를 한 흐름으로. 채널 이동 없음.
- **신뢰 + 대화** — 검증된 정보(뉴스·공시·AI)와 커뮤니티 글이 같은 맥락에 공존.
- **효율** — AI 3줄 요약, 타입 필터.
- **실시간** — 접속 중엔 시세·새 이벤트가 실시간 갱신.

### 1.6 제약사항 (설계를 규정하는 외부 조건)

아래 외부 제약이 §2 설계의 형태를 정한다. 특히 KIS의 세션당 41건 한도가 수요 기반 구독(ADR A2)의 직접 원인이다.

| 제약 | 내용 | 설계 대응 |
|---|---|---|
| KIS WS 등록 한도 | **1세션 실시간 합산 41건, 계좌(앱키)당 1세션**. 한 PC에서 여러 계좌 세션 가능 | 수요 기반 구독 + 다계정 세션풀 |
| KIS REST 유량 | **실전 20건/초, 모의 2건/초 (계좌 단위)**, `tokenP`는 1건/초 | 워커 내 레이트리미터, 배치 페이싱 |
| KIS 토큰 | 접근토큰 24h 유효, **재발급 1분 제한** | Redis 토큰 캐시 + 발급 분산락 |
| ⚠️ 유량 정책 변동 | KIS 포털에 "신규 고객 초당 호출 제한 안내(2026-03-20)" 공지 존재 | **착수 전 포털 공지 원문 확인**(로드맵 체크리스트) |
| 코스콤 라이선스 | 실시간 시세 일반 재배포는 정보시세 이용계약 필요. AI 가공도 면책 아님 | §6, 지연 모드 스위치 |
| OpenDART | 키당 일일 호출 한도 존재 | 분기 시즌 분산 수집 |
| 팀 구성 | 2인 (민균: core-api+KIS 워커+뉴스 파이프라인(ingest/llm) / 팀원: 게이트웨이) | 문서·계약 기반 협업, `:contracts` 공유 |

### 1.7 범위 제외 (Out of Scope)

주문/잔고 등 매매 기능, 해외주식, NXT(대체거래소) 시세, 대댓글, 모바일 네이티브 앱, 소셜 로그인(확장 후보).

## 2. 설계

### 2.1 시스템 아키텍처 — 4개 처리 평면

**모듈러 모놀리스(core-api) + 런타임 특성이 다른 것만 분리한 워커/게이트웨이.** MSA가 아니다.

평면을 나눈 기준은 런타임 특성이다. 지연에 민감하고 상태를 가진 실시간 경로, 느려도 유실되면 안 되는 소식 가공, 무상태로 스케일아웃하는 동기 API, 스케줄로 도는 배치는 확장·장애·배포 특성이 서로 다르다(§2.2). 이렇게 나눠야 메인서버 배포가 WS 연결에 영향을 주지 않고(NFR-06) KIS 유량·키 관리도 워커에 격리된다(ADR A7).

```
① 실시간 평면
   KIS WS ─► worker-price ─► Redis Pub/Sub (quote:{code}) ─► gateway ─► 클라(STOMP)
                        └──► Redis price:{code} (스냅샷 캐시)
 
② 비동기 가공 평면 (소식)
   뉴스/공시 ─► worker-ingest ─► queue:ingest (Redis Streams)
                                   └► worker-llm ─► ①DB 저장 ②PUBLISH stream:{code} ③XACK
 
③ 동기 API 평면
   클라 ─(REST)─► core-api (Spring Modulith 7모듈) ─► PostgreSQL / Redis
                     └─ 글 작성 시: ①DB 저장 ②PUBLISH post:{code}   (더블라이트)
 
④ 배치 평면
   KIS REST + 마스터파일 + OpenDART ─► worker-batch ─► PostgreSQL (마스터·봉·수급·재무)
```

### 2.2 컴포넌트 & 담당

| 앱/모듈 | 역할 | 런타임 특성 | 담당 |
|---|---|---|---|
| `core-api` | REST 7모듈 (auth·search·subscription·stream·notification·community·stockinfo) | Spring MVC, 무상태 ×N | **민균** |
| `worker-price` | KIS WS 실시간 수집·conflation·발행, REST 스냅샷 폴링/봉 수집 | 상태有, 단일(리더 락) | **민균** |
| `worker-batch` | 종목마스터·수급·밸류에이션·투자의견·재무(OpenDART) 스케줄 수집, 신규 투자의견 persist→publish | 스케줄, 단일 | **민균** |
| `gateway` | STOMP 수용, 관심목록 해소, Redis 구독→fan-out, **수요 카운트 유지** | MVC STOMP 브로커, 상태有 | 팀원 |
| `worker-ingest` | 뉴스/공시 수집 → `queue:ingest` XADD | 스케줄/폴링 | **민균** |
| `worker-llm` | 큐 소비→LLM 요약→persist→publish→ack | 무상태 ×N | **민균** |
| `:contracts` | 채널명·봉투 DTO·eventId 규약 상수 | 라이브러리 | 공동 |
| `:kis-client` | KIS 인증(토큰/Approval)·레이트리미터·REST/WS 클라이언트 | 라이브러리 | 민균 |

### 2.3 정보 구조 — StreamEvent & 타입 매핑 (정합성 확정)

모든 이벤트를 하나의 모델로 정규화한다. **v1의 타입 명칭을 WS 명세와 아래처럼 정렬**한다.

| DB `stream_event.type` | WS 봉투 `type` | WS `data.category` | 생산자 | 비고 |
|---|---|---|---|---|
| `NEWS` | `stream` | `news` | worker-llm | 뉴스 AI 요약 포함 |
| `DISCLOSURE` | `stream` | `disclosure` | worker-llm | 공시 |
| `REPORT` | `stream` | `report` | worker-llm · worker-batch | 일반 리포트 + `kind=opinion` 증권사 투자의견 |
| `AI` | `stream` | `ai` | worker-llm | 일일 브리핑·종합 분석 |
| `POST` | `post` | — (`data.kind`=post/comment) | core-api | (v1의 COMMUNITY에서 개명) |
| `PRICE_ALERT` | `stream` | `alert` *(예약)* | worker-price (P3) | WS category에 `alert` 추가 예약 |

core-api의 `StreamEventType`은 이 표의 REST 필터 토큰과 DB 저장 타입 대응을 소비한다. 표의 타입을 바꿀 때 `StreamEventType`과 계약 테스트를 함께 갱신한다.

핵심 필드: `event_id`(ULID·정렬/커서 기준) · `code` · `type` · `occurred_at` · `source` · `payload`(타입별 JSONB). 스트림 조회/필터/알림/페이지네이션이 타입 무관 동일 로직으로 동작한다.

### 2.4 핵심 설계 결정 기록 (ADR 요약)

아키텍처를 규정한 결정 8건과 트레이드오프의 요약이다.

| # | 결정 | 근거/트레이드오프 |
|---|---|---|
| A1 | 모듈러 모놀리스 + 워커 분리 | 2인 팀 운영 부담 최소화. 경계는 Spring Modulith로 강제, 미래 분리 경로 확보 |
| A2 | 수요 기반 KIS 구독 + 다계정 세션풀 | 41건/세션·앱키당 1세션 제약 극복. 수요 = 접속자 관심목록 ∪ 입장 방 |
| A3 | persist → publish → ack/mark | DB가 진실, WS는 best-effort. 뉴스는 PEL, 투자의견은 `published_at IS NULL` 스캔으로 재시도하고 클라이언트 누락은 REST로 복구 |
| A4 | 알림 fan-out-on-read | 이벤트×유저 알림 행 폭증 방지. `cursor:{userId}:{code}` 이후 집계 |
| A5 | ULID 커서 (양방향) | 시간 내포·충돌 없음. 과거 페이지네이션과 재접속 복구를 동일 API로 |
| A6 | 글 더블라이트 (PG + Redis pub) | 저장 커밋 후 발행(AFTER_COMMIT)로 유령 이벤트 방지 |
| A7 | core-api는 KIS 무접촉 | KIS 호출은 워커 전담. core-api는 DB/Redis만 읽음 → 유량·키 관리 단순화 |
| A8 | 주/월봉은 일봉에서 파생 | KIS 호출 절약. 일봉만 적재하고 조회 계층에서 집계 |

### 2.5 정합성 검증 결과 (v1 → v2 변경 사항)

기존 문서 3종을 교차 검토해 찾은 불일치와 확정안이다. **이 표가 v2의 존재 이유다.**

| # | 항목 | v1/기존 문서의 불일치 | v2 확정 |
|---|---|---|---|
| 1 | 서비스 명칭 | 기획안=TickTalk, 기술문서·코드=Alpha Talk | **Alpha Talk로 통일** |
| 2 | 실시간 시세 구독 범위 | 기획안 §5.D "방 입장 종목만" ↔ WS 명세 §3.1 "접속 유저 관심목록 전체를 `/user/queue/quote`로" | **WS 명세 기준 채택**: `quote`=접속 유저 관심목록 전체(가벼운 conflated 틱), `trade`/`depth`=입장 방만(무거움). KIS 수요 = 관심목록 ∪ 입장 방, 용량 초과 시 강등(워커 명세 §2.7) |
| 3 | StreamEvent 타입 명칭 | 기획안 ANALYST·COMMUNITY ↔ WS category `report`, WS type `post` | §2.3 매핑 표로 확정 (REPORT·POST로 개명, `alert` 예약) |
| 4 | 읽음 위치의 기준 | 기획안 "lastReadAt(시각)" ↔ Redis 계약 "cursor = 마지막 eventId" | **eventId(ULID) 기준으로 통일** — 동시각 충돌 없음, 복구 API와 일원화 |
| 5 | 워커 구성 | 기획안 §10 "워커 3종(ingestion=시세)" ↔ Redis 계약은 price/ingest/llm 구분 | **4종 확정**: price(KIS 시세)·ingest(뉴스 수집)·llm(요약)·batch(마스터/펀더멘털) |
| 6 | `stream` 명칭 충돌 | Pub/Sub 채널 `stream:{code}` vs Redis Streams 자료구조 | 리네임(`feed:{code}`)은 **보류**, 대신 `:contracts` 상수로만 참조(문자열 하드코딩 금지). 팀 합의 안건 |
| 7 | 커서 저장 내구성 | Redis 단독이면 유실 시 전부 미읽음으로 복귀 | Redis(fast path) + DB `read_cursor`(write-through 미러)로 이원화 |

### 2.6 화면 구성 (v1 유지)

## 3. 구현 계획

### 3.1 저장소 구조 (Gradle 멀티모듈 모노레포)

**한 저장소(`backend/`)에 여러 Gradle 서브모듈을 담고 각 서버는 독립 실행·배포되는 모듈이다.** 단, 모든 폴더가 서버는 아니다 — 서버(bootable app)와 공유 라이브러리(bootable 아님)를 구분한다.

```
backend/                        # 저장소 루트 (Gradle rootProject = "alphatalk")
├─ settings.gradle.kts          # 서브모듈 include 목록
├─ build.gradle.kts             # 공통 컨벤션 (subprojects{} 또는 build-logic 컨벤션 플러그인)
├─ gradle/libs.versions.toml    # 버전 카탈로그 (전 모듈 공용)
├─ docker-compose.yml           # 로컬 인프라 (PostgreSQL·Redis)
│
│   # ── 라이브러리 (서버 아님, 다른 모듈이 의존) ──────────────
├─ contracts/        # 채널명·키·STOMP 목적지·봉투 DTO·eventId 규약 (Spring 무의존)   [공동]
├─ auth-jwt/         # JWT 발급(TokenIssuer)·검증(TokenVerifier) — core-api·ws 공유    [공동]
├─ kis-client/       # KIS 인증·유량제어·REST/WS 클라이언트                            [민균]
├─ db-migrations/    # DB 스키마 마이그레이션(Liquibase changelog) — 전 서버 공용       [공동]
│
│   # ── 서버 (각각 독립 배포되는 Spring Boot 앱) ──────────────
├─ core-api/         # 메인서버 — REST, Spring MVC + Modulith 7모듈                   [민균]
├─ ws/               # WS 게이트웨이 — MVC + STOMP 브로커 (구 gateway)                 [팀원]
├─ worker-price/     # KIS 실시간 시세 수집·conflation·발행                            [민균]
├─ worker-batch/     # 종목마스터·봉·수급·재무 배치                                   [민균]
├─ worker-ingest/    # 뉴스/공시 수집 → queue:ingest                                  [민균]
├─ worker-llm/       # 큐 소비 → LLM 요약 → persist·publish·ack                       [민균]
│
└─ infra/            # docker-compose 확장·(P4) Terraform·운영 스크립트
```

> **명칭 확정**: WS 게이트웨이 모듈은 `ws`로 한다 (문서상 별칭 "gateway"는 병기만). WS 문서·계약(§0)의 모듈명과 일치.

#### 모듈 성격 & 의존

| 모듈 | 종류 | 스택 | 로컬 포트 | 의존 (라이브러리만) |
|---|---|---|---|---|
| `contracts` | 라이브러리 | Kotlin, Spring 무의존 | — | (없음 — 순수) |
| `auth-jwt` | 라이브러리 | Kotlin — 코어는 순수, Boot 자동구성 동봉(스타터형): 의존성 + `alphatalk.auth.jwt.secret`만으로 빈 등록 | — | (jjwt 내장) |
| `kis-client` | 라이브러리 | Kotlin/Java, Resilience4j | — | (독립 — KIS 도메인) |
| `db-migrations` | 라이브러리 | Liquibase changelog 리소스 + liquibase-core 노출 — DB 쓰는 서버가 의존하면 기동 시 자동 적용 | — | (liquibase-core 내장) |
| `core-api` | **서버** | Spring MVC + Modulith | 8080 | `contracts`, `auth-jwt`(발급+검증), `db-migrations` |
| `ws` | **서버** | Spring MVC + STOMP 브로커 | 8081 | `contracts`, `auth-jwt`(검증만) |
| `worker-price` | **서버** | Spring Boot (상태有, 리더락) | 8082(actuator) | `contracts`, `kis-client` |
| `worker-batch` | **서버** | Spring Boot (스케줄, ShedLock) | 8083(actuator) | `contracts`, `kis-client`, `db-migrations` |
| `worker-ingest` | **서버** | Spring Boot (폴링) | 8084(actuator) | `contracts` |
| `worker-llm` | **서버** | Spring Boot (무상태 ×N) | 8085(actuator) | `contracts`, `db-migrations` |

**의존 규칙 (아키텍처 경계 = 빌드 그래프로 강제):**
- 서버 모듈은 **라이브러리에만** 의존한다. **서버 → 서버 의존 금지** (서버 간 통신은 코드 의존이 아니라 Redis/DB 계약으로만).
- `contracts`는 아무것도 의존하지 않는 순수 모듈 (전 서비스가 공유하는 단일 진실).
- `core-api`는 KIS를 만지지 않으므로 `kis-client`에 의존하지 않는다 (ADR A7).
- 순환 의존은 Gradle이 빌드 타임에 거부한다.

#### `settings.gradle.kts` (골격)

```kotlin
rootProject.name = "alphatalk"
include("contracts", "auth-jwt", "kis-client", "core-api", "ws",
        "worker-price", "worker-batch", "worker-ingest", "worker-llm")
```

각 서버 모듈은 자체 `bootJar`·`application.yml`·main 클래스·Dockerfile을 가진다. 라이브러리 모듈은 `java-library`(또는 Kotlin) 플러그인만 쓰고 boot 플러그인을 적용하지 않는다. 공통 Kotlin/JVM21 toolchain·테스트 설정은 루트 `subprojects{}` 또는 `build-logic` 컨벤션 플러그인으로 한 곳에서 관리한다.

#### 실행 (모듈별 독립)

```bash
docker compose up -d            # 로컬 인프라 (PG·Redis)
./gradlew :core-api:bootRun     # 메인서버
./gradlew :ws:bootRun           # WS 게이트웨이
./gradlew :worker-price:bootRun # 시세 워커
./gradlew build                 # 전 모듈 빌드+테스트
```

#### 스캐폴딩 순서 (한 번에 다 만들지 않는다)

M0에서 뼈대만: **`contracts` → `ws`(+임시 stub) → `core-api`** 순으로 빈 앱을 세우고 빌드 그래프를 확정한다. 워커(`worker-*`)와 `kis-client`는 해당 마일스톤(M2 이후)에서 추가한다. 지금 당장은 `settings.gradle.kts`에 있는 모듈만 include하고 나머지는 착수 시점에 등록한다.

## 5. 배포·운영 설계

### 5.1 환경

환경은 local · dev/staging · prod(데모) 3단계다. 실전 KIS 키는 prod 데모 시연에만 쓴다(§4 원칙).

| 환경 | KIS | 인프라 | 용도 |
|---|---|---|---|
| local | 모의 | docker-compose (PG+Redis) | 개발 |
| dev/staging | 모의 | 데모 트랙과 동일 구성 | 통합·E2E |
| prod(데모) | 실전(비공개) 또는 모의 | 아래 2트랙 | 포트폴리오 시연 |

**2트랙 배포**: ① *데모 트랙(저비용)* — EC2 1대 + docker-compose(전 서비스+PG+Redis), ② *정식 트랙(P4)* — ECS Fargate + RDS + ElastiCache, Terraform. M6까지는 데모 트랙으로 충분하다.

### 5.2 CI/CD

PR: 빌드→단위/계약 테스트→Modulith verify → main 머지: 통합 테스트(Testcontainers)→이미지 빌드/푸시→배포(수동 승인). 시크릿은 GitHub Secrets/SSM, 저장소 커밋 금지.

### 5.3 관측성 (핵심 메트릭)

`kis_ws_sessions` · `kis_subscribed_symbols` · `tick_in/out_rate` · `conflation_lag` · `rest_call_rate`/`rest_throttled` · `token_refresh_total` · `queue_ingest_pending(PEL)` · `stream_api_p95` · `batch_job_duration/fail` · `ws_connected_clients`. 알람: KIS 세션 전멸, PEL 적체 > N, 배치 실패, 예산 초과.

### 5.4 장애 시나리오 & 대응

| 시나리오 | 영향 | 대응 |
|---|---|---|
| Redis 다운 | 틱/푸시 중단, 캐시 유실 | 틱은 드랍 허용(다음 틱 대체). 복구 후 커서는 DB 미러에서 재적재. 소식은 DB에 있어 REST 조회 무영향 |
| KIS 점검/장애 | 실시간·배치 중단 | 지수 백오프 재접속, 배치 다음 슬롯 재시도. 상단 핀 `delayed` 표기 |
| gateway 재기동 | WS 단절 | 클라 백오프 재연결 → 관심목록 재해소 → REST 커서 복구 (WS 명세 §7) |
| core-api 배포 | 없음(WS 무영향) | 무중단 롤링 |
| worker-price 크래시 | 틱 공백 | 리더 락 회수 후 재기동, 수요 해시 리컨실로 재구독 |

백업: PG 일 스냅샷. `stream_event` 파티션 보존 12개월 후 아카이브/삭제 정책.

## 6. 법적 / 라이선스 고려사항

> ⚠️ 사실 정리이며 법률 자문이 아니다. 일반 공개 전 실제 약관·전문가 확인 필수.

- **실시간 시세 재배포**: KRX/코스콤 정책상 일반 재배포는 **코스콤 정보시세 이용계약** 필요. 시세정보 정의는 **가공·편집 데이터 포함** → AI 재가공도 자동 면책 아님. (생성 후 20분 경과분은 비실시간 간주)
- **현실 경로**: ① 공개 표시는 지연(20분+) 데이터 기반 — NFR-08의 **지연 모드 스위치**로 전환 가능하게 설계 ② 코스콤 라이선스 취득(7년 미만 핀테크 법인 수수료 면제 가능) ③ 개인 포트폴리오/내부 데모는 저위험, 일반 공개 순간 재배포 영역.
- **호가 제한**: 일반 제공 시 호가 제외, 제3자 재가공 수단(API) 제공 금지 등 제약.
- **뉴스·컨센서스**: 본문 저작권 → 요약+원문 링크 방식. 컨센서스는 상용 라이선스(FnGuide 등) 확보 전 미제공.
- **면책 고지**: 모든 정보·AI 산출물은 투자 권유가 아닌 참고용.
